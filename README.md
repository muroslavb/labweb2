# Лабораторна робота №2 — Клієнтський застосунок "Бібліотека"

Простими словами: SPA-застосунок (сторінка без перезавантажень) на TypeScript,
webpack, Bootstrap, з валідацією форм, збереженням у LocalStorage і юніт-тестами.

## Як запустити

1. Розпакуй проєкт, відкрий у VS Code.
2. У терміналі: `npm install`
3. Щоб побачити застосунок у браузері: `npm start` — відкриється
   http://localhost:9000, і при зміні коду сторінка сама оновлюється.
4. Щоб зібрати продакшн-версію: `npm run build` (з'явиться папка `dist`).
5. Щоб прогнати тести: `npm test`
6. Щоб перевірити стиль коду: `npm run lint`

## Структура проєкту (за шарами відповідальності)

```
src/
├── models/          — "що таке книга/користувач" (дані + методи)
├── services/         — бізнес-логіка (Library<T>, Storage)
├── utils/            — валідація, генератор ID
├── ui/components/    — все, що малює інтерфейс
├── types/            — спільні типи
└── app.ts            — точка входу, з'єднує все разом
tests/                — юніт-тести (Mocha + Chai)
```

## Пояснення кожного файлу простими словами

### `models/interfaces/IBook.ts`, `IUser.ts`
"Анкета" — які поля обов'язково повинні бути у книги/користувача.

### `models/Book.ts`, `User.ts`
Самі класи. `Book` вміє позначати себе позиченою/поверненою
(`markAsBorrowed`, `markAsReturned`). `User` знає, скільки книг вже позичив,
і чи може позичити ще (`canBorrowMore()` — не більше 3-х).

### `services/Library.ts` — **Generic-клас**
```typescript
export class Library<T extends Identifiable> {
  private items: T[] = [];
  add(item: T): void { this.items.push(item); }
  find(id: string): T | undefined { ... }
}
```
`<T>` означає "цей клас працює з будь-яким типом" — один і той самий клас
`Library` ми використовуємо і для книг (`Library<Book>`), і для користувачів
(`Library<User>`), не дублюючи код. `extends Identifiable` — обмеження: тип
`T` обов'язково повинен мати поле `id` (бо `Library` шукає елементи саме за id).

### `services/Storage.ts`
Обгортка над `localStorage` браузера — зберігає й читає дані у форматі JSON,
щоб при перезавантаженні сторінки книги й користувачі нікуди не зникали.

### `utils/idGenerator.ts`
Генерує унікальний числовий ID (поточний час у мілісекундах + випадкові цифри) —
завжди лише цифри, як і вимагає завдання.

### `utils/validators.ts` — **namespace Validation**
```typescript
export namespace Validation {
  export function isValidYear(value: string): boolean { ... }
  export function validateBook(...) { ... }
}
```
`namespace` — це спосіб згрупувати пов'язані функції під одним іменем
(`Validation.validateBook(...)`), щоб було зрозуміло, що вони всі про одне —
перевірку введених даних. Перевіряє: обов'язкові поля, що рік видання —
4 цифри в розумному діапазоні, що email схожий на email, що ID користувача —
лише цифри.

### `ui/components/Modal.ts`
Своє модальне вікно (бо `alert()` заборонено завданням). Використовується і
для повідомлень ("книгу позичено"), і для введення ID користувача при позичанні.

### `ui/components/BookForm.ts`, `UserForm.ts`
Форми додавання книги/користувача. При натисканні кнопки перевіряють дані
через `Validation`, і якщо щось не так — показують текст помилки під полем
(так, як показано на скріншоті дизайну), замість того щоб просто не працювати.

### `ui/components/BookList.ts`, `UserList.ts`
Список книг/користувачів з пошуком (за назвою/автором), кнопками
"Позичити"/"Повернути"/видалити, і пагінацією (5 елементів на сторінку).

### `app.ts` — головний файл
Клас `App`:
1. При старті зчитує книги й користувачів з `localStorage`.
2. Малює всю сторінку (`render()`) — форми, списки.
3. Після будь-якої дії (додав книгу, позичив, видалив) — зберігає в
   `localStorage` і перемальовує сторінку заново.
4. `openBorrowModal` → `confirmBorrow` — логіка позичання: перевіряє ID,
   чи існує такий користувач, чи не перевищив він ліміт (3 книги),
   і лише тоді позначає книгу позиченою.

## Юніт-тести (`tests/`)

- `library.test.ts` — перевіряє `Library<T>`: додавання, пошук, видалення.
- `validation.test.ts` — перевіряє `Validation`: чи ловить порожні поля,
  неправильний рік, неправильний email, нецифровий ID.

Запуск: `npm test`. Усі 13 тестів проходять.

## Husky (pre-commit hook)

Файл `.husky/pre-commit` автоматично запускає `npm run lint && npm test`
**перед кожним комітом**. Якщо лінтер або тести не проходять — коміт
блокується. Це щоб у репозиторій не потрапляв "зламаний" код.

## Feature branch workflow + Conventional Commits (вимоги звіту)

Роби кожну частину функціоналу в окремій гілці, наприклад:
```
git checkout -b feature/book-model
git checkout -b feature/validation
git checkout -b feature/borrow-return
```
Коміти пиши за форматом **Conventional Commits**:
```
feat: додано generic-клас Library<T>
feat: реалізовано валідацію форм книги та користувача
fix: виправлено підрахунок сторінок пагінації
test: додано юніт-тести для Validation
docs: оновлено README
```
Після завершення гілки — Pull Request у `main` (навіть якщо працюєш одна,
це показує розуміння workflow).

## Що ще потрібно зробити вручну (не можна зробити з мого боку)

Пункти 22–24 із завдання вимагають дій безпосередньо в твоєму GitHub-акаунті:

1. **Гілка `vite-migration`** — створи нову гілку, видали `webpack.config.js`
   і webpack-залежності з `package.json`, встанови `vite` (`npm install -D vite`),
   створи `vite.config.ts` (можу допомогти написати конкретний конфіг, якщо
   скажеш — з чим саме виникли труднощі).
2. **Деплой на gh-pages** — `npm install -D gh-pages`, додати скрипт
   `"deploy": "gh-pages -d dist"` у `package.json`, викликати `npm run build && npm run deploy`.
3. **Висновок webpack vs Vite** — напиши у README після того, як попрацюєш з
   обома: зазвичай Vite стартує швидше (не бандлить усе одразу, а віддає
   модулі на льоту), простіше налаштовується, але для зовсім маленьких
   проєктів різниця не завжди відчутна.

Якщо дійдеш до цих пунктів і щось не вийде — покажи помилку, розберемось так
само, як з `npm`/PowerShell раніше.
