# Контрольні запитання — прості відповіді (для захисту)

**1. Переваги TypeScript у великому застосунку?**
Типи ловлять помилки одразу при написанні коду, а не після запуску. У великому
проєкті з багатьма файлами це рятує від "забула передати не той тип" помилок.

**2. Клас vs інтерфейс?**
Клас — це "жива" сутність: має і опис полів, і реалізацію методів, можна
створити об'єкт (`new`). Інтерфейс — тільки опис "що повинно бути", без
реалізації, об'єкт створити не можна. Інтерфейс варто використовувати, коли
треба просто описати форму даних — наприклад `IBook` описує, які поля повинні
бути в книги, а сам клас `Book` вже додає логіку (методи).

**3. Навіщо Generics у Library?**
Без Generics довелось би писати окремий клас `BookLibrary` і окремий
`UserLibrary` з однаковим кодом всередині (дублювання). `Library<T>` — це
один клас, який працює з будь-яким типом `T`. Якби не generic — `Library`
довелось би або дублювати, або зробити з типом `any`, і тоді ми б втратили всю
перевірку типів (можна було б випадково покласти користувача в бібліотеку книг).

**4. Модулі vs namespace?**
Модуль (ES-модуль) — це окремий файл з `import`/`export`, стандартний спосіб
ділити код у сучасному TS/JS. `namespace` — спосіб згрупувати пов'язаний код
**всередині** модуля під одним іменем (наприклад `Validation.validateBook(...)`),
коли хочеться логічно об'єднати кілька функцій без створення купи окремих
файлів. У нашому проєкті `namespace Validation` живе всередині файлу-модуля
`validators.ts`.

**5. Як організована модульна структура (models, services, utils)?**
`models` — тільки дані й методи доступу до них, нічого не знають про UI чи
збереження. `services` — бізнес-логіка (`Library<T>`, `Storage`), теж без
DOM. `utils` — прості допоміжні функції (валідація, генерація ID), які нічого
не знають ні про UI, ні про дані. Це розділення дозволяє змінювати один шар
(наприклад, спосіб малювання UI), не ламаючи інші.

**6. Як працює Storage/LocalStorage? Обмеження LocalStorage?**
`Storage.save(key, data)` перетворює дані на текст (`JSON.stringify`) і кладе
в `localStorage` браузера; `Storage.load(key)` читає текст назад і перетворює
в об'єкт (`JSON.parse`). Обмеження: зберігає лише текст (тому обов'язково
JSON.stringify/parse), максимум ~5-10 МБ, дані зберігаються тільки в одному
браузері на одному пристрої (не синхронізуються між пристроями).

**7. Логіка borrow/return?**
`borrow` (`confirmBorrow`): перевіряє ID користувача → чи існує такий
користувач → чи не перевищив ліміт (3 книги) → якщо все ок, викликає
`book.markAsBorrowed(userId)` і `user.addBorrowedBook(bookId)`, зберігає й
перемальовує UI (кнопка стає "Повернути"). `return`: викликає
`book.markAsReturned()` і `user.removeBorrowedBook(bookId)` — кнопка знову
стає "Позичити".

**8. Як реалізована валідація форм?**
Функції в `namespace Validation`: `isRequired` перевіряє непорожність,
`isValidYear` перевіряє регуляркою `/^\d{4}$/`, що рік — рівно 4 цифри, і
додатково що число в розумному діапазоні (1450 – поточний рік).
`isDigitsOnly` (`/^\d+$/`) перевіряє, що ID користувача — лише цифри.

**9. Ліміт позичених книг?**
Не більше 3-х книг на одного користувача (`MAX_BORROWED_BOOKS = 3` в
`User.ts`). Перевіряється методом `user.canBorrowMore()`. Якщо ліміт
перевищено — модальне вікно показує повідомлення про це замість того, щоб
дозволити позичити ще одну.

**10. Чому заборонена розмітка в index.html?**
Щоб довести, що ти вмієш будувати інтерфейс програмно через TypeScript/DOM
API, а не просто писати статичний HTML. `index.html` містить лише
`<div id="app"></div>`, а весь вміст (форми, списки, кнопки) генерується
кодом у `ui/components/*.ts` через `document.createElement`/`innerHTML`
всередині JS.

**11. За що відповідає webpack.config.js?**
`entry` — з якого файлу починати збірку (`./src/app.ts`). `output` — куди
класти готовий файл (`dist/bundle.js`). `module.rules` — як обробляти різні
типи файлів (`ts-loader` для `.ts`, `style-loader`+`css-loader` для `.css`).
`devServer` — налаштування локального сервера розробки (порт 9000,
автовідкриття браузера).

**12. Роль ESLint і Prettier?**
ESLint шукає **помилки й погані практики** в коді (наприклад, невикористана
змінна). Prettier лише **форматує** код (відступи, лапки, крапки з комою) —
йому байдуже, чи код "правильний", тільки як він виглядає. Тому їх
використовують разом: ESLint — для якості коду, Prettier — для однакового
стилю.

**13. Що тестують юніт-тести?**
Для `Library<T>`: чи правильно додає елемент, чи знаходить за id, чи видаляє,
чи шукає за умовою. Приклад тест-кейсу:
```typescript
it('знаходить елемент за id', () => {
  const library = new Library<TestItem>();
  library.add({ id: '1', value: 'a' });
  expect(library.find('1')?.value).to.equal('a');
});
```
Для `Validation`: чи ловить порожні поля, неправильний рік, неправильний
email, нецифровий ID.

**14. Як працює Husky pre-commit?**
Перед кожним `git commit` автоматично запускається скрипт
(`npm run lint && npm test`). Якщо лінтер знайшов помилки або хоч один тест
впав — коміт **не відбувається**. Це вирішує проблему "хтось закомітив
зламаний код" у командній розробці: неякісний код просто не потрапить у
репозиторій.

**15. webpack vs Vite (порівняння)?**
Vite зазвичай стартує dev-сервер значно швидше, бо не збирає весь проєкт
одразу, а віддає файли по запиту браузера (ES-модулі нативно). Конфігурація
Vite зазвичай коротша й простіша, ніж `webpack.config.js`. Розмір
продакшн-збірки в обох подібний (Vite використовує Rollup для продакшн-білда).
Для невеликих SPA, як цей проєкт, Vite суб'єктивно зручніший через швидкість
і мінімум налаштувань; webpack гнучкіший і має більшу екосистему плагінів для
складних/легасі проєктів.
